\section{Empirical Evaluation}\label{sec:empirical-evaluation}

This section evaluates whether the implemented optimization pipeline improves Router accuracy under controlled conditions. All experiments use the synthetic data introduced in \cref{sec:golden-dataset}, since Interhyp could not provide production queries. The reported results therefore demonstrate the behavior of the pipeline on the project datasets rather than its performance under live broker traffic.

Both datasets were drawn as disjoint subsets of Stage 4 of the four-stage golden dataset (\cref{sec:dataset-stages}). A fixed set of 240 queries was reserved exclusively for baseline and final evaluation, while a separate set of 1,000 queries was used to generate judge feedback and optimize the Stage 2 prompt. This separation tests whether the optimized prompt generalizes beyond the data used for optimization rather than merely fitting it. In a production setting, the equivalent safeguard would be to optimize on judge-labelled production traffic and validate a candidate prompt on a separate human-labelled sample before prompt deployment.

The experiments also distinguish the two routing stages described in \cref{sec:router}. The embedding model in Stage 1 performs similarity-based routing through the vector store, whereas Stage 2 uses the LLM-based Router and its versioned system prompt. The main optimization experiment deliberately isolates Stage 2. This mirrors Interhyp's current production setup, which has no direct equivalent of the implemented Stage 1, and makes it possible to attribute changes in accuracy to prompt optimization rather than to additions to the vector store.

\subsection{Baseline: Stage 2 with the Original Prompt}\label{sec:empirical-baseline}

The baseline was measured in the Evaluation Dashboard on the fixed set of 240 queries. Stage 1 was deliberately disabled by not containing any queries in the vector store to ensure that every query is routed via Stage 2. The Stage 2 system prompt was intentionally simple and contained only a short routing instruction, broad descriptions of the eight agents, and a small number of few-shot examples. This configuration approximated the routing approach available at Interhyp at the beginning of the project and therefore provided the relevant point of comparison for the optimization pipeline. The baseline Router correctly routed 200 of the 240 evaluation queries, corresponding to 83\% accuracy, with an average latency of 669 ms.

The aggregate result concealed a severe agent-level failure. When \texttt{PlatformSupportAgent} was the golden label, the Router did not select it for any query, resulting in an agent-level accuracy of 0\%. Performance was also uneven beyond \texttt{PlatformSupportAgent}. \texttt{GeneralPurposeAgent} reached 83\% accuracy and was frequently confused with \texttt{PropertyReviewAgent}, while \texttt{OfferAgent} reached 87\% and was likewise often routed to \texttt{PropertyReviewAgent}. Because the baseline prompt supplied only broad descriptions and few examples, it did not define sufficiently clear boundaries between fallback queries, requests to review property documents, and requests to create an offer. The confusion matrix therefore shows over-selection of \texttt{PropertyReviewAgent} rather than random errors. These agent-level disparities show why overall accuracy alone is insufficient in a multi-agent system. A Router can appear broadly functional while systematically failing or over-selecting individual agents.

\subsection{Generation of Judge Labels}\label{sec:empirical-judge-labels}

The next step was to use the Training Dashboard to process the separate 1,000-query training dataset. For each query, the Router produced a routing decision and the judge compared the selected agent's answer with the answer of the strongest alternative available from the Router's candidate ranking. The resulting verdict and reasoning formed the feedback signal for prompt optimization.

Although the Training Dashboard can normally write judge-confirmed examples back to the Stage 1 vector store, this functionality was disabled for the experiment. Enabling it would have caused changes in two components at once: new examples could have improved Stage 1 while OPRO modified the Stage 2 prompt. Disabling write-back therefore ensured that any observed improvement had to result from changes to Stage 2.

The 1,000 training queries and 240 evaluation queries remained disjoint throughout the experiment. The judge labels and explanations from the training data were available to the optimizer, but the golden labels of the evaluation queries were not. The final evaluation therefore tests whether the optimized routing rules for the Router generalize beyond the cases that produced the optimization signal.

\subsection{Optimization}\label{sec:empirical-optimization}

The judge-labelled training runs were passed to the OPRO-based optimizer described in \cref{sec:optimizer}. OPRO treats the Stage 2 system prompt as the optimization variable. In each round the optimizer proposes candidate prompts based on the existing prompt trajectory, routing examples, limited hard formatting rules and the judge's explanations of previous failures. Each candidate is installed temporarily, evaluated again on the training cases, and assigned a routing score, and the strongest candidate is retained for the next round. The strongest prompt reached 99\% golden-label accuracy by the second optimization run.

The speed of that convergence is worth examining, because the seed prompt was not a weak starting point as it already reached 83\% accuracy. What remained were the agent-boundary distinctions, and the judge's explanations of individual failures supplied exactly that. Once those were addressed, in the second run, only six training queries were misrouted, leaving almost no error signal for later rounds to act on. The convergence is therefore a consequence of the error distribution rather than of a poor starting prompt.

\subsection{Divergence Between Judge Labels and Golden Labels}\label{sec:empirical-label-divergence}

As the training queries were also labelled with predefined golden labels, it was possible to evaluate if the agent selected by the Router matched the golden label and whether the judge preferred the expected agent's generated answer over the alternative answer. On the complete 1,000-query training run used in this final experiment, the strongest prompt achieved 99\% accuracy against the golden labels, while the judge-derived evaluation reported 94\% for the same configuration.

\caption{Training Dashboard for the 1,000-query run. The Router matched 994 golden labels (99\%), while judge agreement with ground truth was 94\%, with 58 judge-label mismatches (Chatbot application).}
\label{fig:empirical-label-comparison}
\end{figure}
\FloatBarrier

The five-percentage-point gap does not necessarily mean that either measurement is internally inconsistent. The two signals measure related but non-identical targets. The golden label grades a closed-set classification decision as it asks whether the Router selected the agent assigned to the query when the dataset was created. The judge instead performs a pairwise assessment of generated answers. Its verdict therefore depends not only on the expected agent class, but also on the particular answers generated for that run and on which alternative agent the Router placed next in its ranking. Three mechanisms can consequently produce disagreement:

\begin{enumerate}
\item \textbf{Ambiguous task boundaries.} Some synthetic queries plausibly fit more than one agent. The golden dataset must nevertheless assign one label, whereas two candidate agents may both return useful answers. The judge can prefer the alternative even when the Router selected the predefined golden agent.
\item \textbf{Answer-generation variance.} The judge is intended to assess routing decisions, but it does so by comparing the answers produced by the selected agent and the strongest alternative. Variation in those answers can therefore make a correct route appear worse, or an incorrect route appear better, in a particular run.
\item \textbf{Router-dependent candidate selection.} The judge compares the selected answer with a high-ranked alternative rather than independently classifying the query across all eight agents. If the correct agent is absent from the compared candidates, the judge cannot recover it. As the Router prompt changes, the candidate pairs presented to the judge change as well.
\end{enumerate}

Despite the difference in absolute values, judge-assessed accuracy moved in the same direction as golden-label accuracy across the optimization runs. Configurations with higher golden-label accuracy also received higher judge-assessed accuracy. The judge signal was therefore useful for ranking prompt candidates and steering optimization, even though it did not reach perfect agreement with the ground-truth labels. The 94\%-rated prompt was the best-performing candidate according to the signal available to the optimization pipeline and was consequently selected to be evaluated for deployment.

In a production environment, golden labels are unavailable for production traffic, so the judge becomes the only operational reference signal. If the same discrepancy occurred in production, monitoring would report 94\% even though a later human-labelled audit might estimate performance closer to 99\%. Without periodically sampled human labels, neither the direction nor the size of the gap can be assumed to remain constant. The practical implication is that judge-based monitoring can guide optimization, but it should be calibrated periodically against independently labelled samples, as already concluded with Julian Kappler and Rainer Bomblies during the Sprint 3 review (\cref{sec:sprint3-review}).

\subsection{Final Evaluation and Deployment}\label{sec:empirical-final}

The prompt selected in the first experiment was saved as a new Stage 2 prompt version and deployed in the showcase application. Re-running Stage 2 alone on the fixed 240-query evaluation set produced 100\% routing accuracy, compared with the 83\% baseline.

\begin{figure}[htbp]
\centering
\includegraphics[width=1\linewidth,height=0.78\textheight,keepaspectratio]{assets/evaluation/optimized-stage2.png}
\caption{Evaluation Dashboard for the optimized Stage 2-only configuration. The Router correctly classified all 240 evaluation queries.}
\label{fig:empirical-optimized-stage2}
\end{figure}

Because the dataset and routing stage remained unchanged, this 17-percentage-point improvement can be attributed to the optimized Stage 2 prompt within the experimental setting.

The final run then restored the complete two-stage pipeline. Judge-confirmed examples from the separate 1,000-query training set were written to the Stage 1 example store, while Stage 2 reused the optimized prompt because it had already reached 100\% accuracy on the fixed evaluation set. This allowed the final experiment to measure how much Stage 1 could reduce LLM use while preserving the Stage 2 accuracy gain. The resulting two-stage configuration reached 98\% accuracy while resolving 188 of the 240 queries through Stage 1. Stage 1 therefore covered 78\% of the dataset and avoided the corresponding Stage 2 LLM calls. Average latency decreased from 669 ms to 407 ms, a reduction of 262 ms or 39\%. This measured reduction is conservative relative to a production deployment because the prototype generated embeddings on the project's comparatively slow Python worker. Using a production-grade embedding model provider would substantially reduce Stage 1 latency and therefore make the overall latency saving considerably larger. The two-percentage-point reduction relative to the optimized Stage 2-only configuration was the accepted trade-off for the efficiency improvement. These configurations answer different empirical questions. The Stage 2-only comparison isolates the effect of prompt optimization, whereas the two-stage result evaluates the accuracy--efficiency trade-off of the complete Router.
