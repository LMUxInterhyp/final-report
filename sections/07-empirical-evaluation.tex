\section{Empirical Evaluation}\label{sec:empirical-evaluation}

This section evaluates whether the implemented optimization pipeline improves Router accuracy under controlled conditions. All experiments use the synthetic data introduced in \cref{sec:golden-dataset}, since Interhyp could not provide production queries. The reported results therefore demonstrate the behavior of the pipeline on the project datasets rather than its performance under live broker traffic.

Both datasets were drawn as disjoint subsets of Stage 4 of the four-stage golden dataset (\cref{sec:dataset-stages}). A fixed set of 240 queries was reserved exclusively for baseline and final evaluation, while a separate set of 1,000 queries was used to generate judge feedback and optimize the Stage 2 prompt. This separation tests whether the optimized prompt generalizes beyond the data used for optimization rather than merely fitting it. In a production setting, the equivalent safeguard would be to optimize on judge-labelled traffic and validate a candidate prompt on a separate human-labelled sample before deployment.

The experiments also distinguish the two routing stages described in \cref{sec:router}. Stage 1 performs similarity-based routing through the vector store, whereas Stage 2 uses the LLM-based Router and its versioned system prompt. The main optimization experiment deliberately isolates Stage 2. This mirrors Interhyp's current production setup, which has no direct equivalent of the implemented Stage 1, and makes it possible to attribute changes in accuracy to prompt optimization rather than to additions to the vector store.

\subsection{Baseline: Stage 2 with the Original Prompt}\label{sec:empirical-baseline}

The baseline was measured in the Evaluation Dashboard on the fixed set of 240 queries. Every query was routed through Stage 2. Stage 1 was disabled. The Stage 2 system prompt was intentionally minimal and contained only a short routing instruction, broad descriptions of the eight agents, and a small number of few-shot examples. This configuration approximated the routing approach available at Interhyp at the beginning of the project and therefore provided the relevant point of comparison for the optimization pipeline.

The baseline Router correctly routed 200 of the 240 evaluation queries, corresponding to 83\% accuracy, with an average latency of 669 ms. The aggregate result concealed a particularly severe class-level failure: when \texttt{PlatformSupportAgent} was the golden label, the Router did not select it for any query, resulting in an agent-level accuracy of 0\%. Performance was also uneven beyond \texttt{PlatformSupportAgent}. \texttt{GeneralPurposeAgent} reached 83\% accuracy and was frequently confused with \texttt{PropertyReviewAgent}, while \texttt{OfferAgent} reached 87\% and was likewise often routed to \texttt{PropertyReviewAgent}. Because the baseline prompt supplied only broad descriptions and few examples, it did not define sufficiently clear boundaries between fallback queries, requests to review property documents, and requests to create an offer. The confusion matrix therefore suggests over-selection of \texttt{PropertyReviewAgent} rather than isolated random errors. These class-level disparities show why overall accuracy alone is insufficient in a multi-agent system: a Router can appear broadly functional while systematically failing or over-selecting individual agents.

\subsection{Generation of Judge Labels}\label{sec:empirical-judge-labels}

The next step used the Training Dashboard to process the separate 1,000-query training dataset. For each query, the Router produced a routing decision and the judge compared the selected agent's answer with the answer of the strongest alternative available from the Router's candidate ranking. The resulting verdict and reasoning formed the feedback signal for prompt optimization.

Although the Training Dashboard can normally write judge-confirmed examples back to the Stage 1 vector store, this functionality was explicitly disabled for the experiment. Enabling it would have changed two components at once: new examples could have improved Stage 1 while OPRO modified the Stage 2 prompt. Disabling write-back therefore created a controlled ablation in which any observed improvement had to result from changes to Stage 2. It also made the experiment more directly relevant to Interhyp's current architecture, which has no Stage 1 equivalent.

The 1,000 training queries and 240 evaluation queries remained disjoint throughout the experiment. The judge labels and explanations from the training data were available to the optimizer, but the golden labels of the evaluation queries were not. The final evaluation therefore tests whether the optimized routing rules generalize beyond the cases that produced the optimization signal.

\subsection{Optimization}\label{sec:empirical-optimization}

The judge-labelled training runs were passed to the OPRO-based optimizer described in \cref{sec:optimizer}. OPRO treats the Stage 2 system prompt as the optimization variable. In each round the optimizer proposes candidate prompts based on the existing prompt trajectory, routing examples, limited hard formatting rules and the judge's explanations of previous failures. Each candidate is installed temporarily, evaluated on the training cases, and assigned a routing score, and the strongest candidate is retained for the next round. The strongest prompt reached 99 per cent golden-label accuracy by the second optimization run.

The speed of that convergence is worth examining, because the seed prompt was not a weak starting point. It was written by the team as a best-effort solution and already performed well, so the optimizer was not correcting obvious defects but refining a prompt that was close to the boundary of what manual writing had achieved. What remained were the agent-boundary distinctions that are hard to articulate by hand, and the judge's explanations of individual failures supplied exactly that. Once those were addressed, only six training queries stayed misrouted, leaving almost no error signal for later rounds to act on. The convergence is therefore a consequence of the error distribution rather than of a poor starting prompt: the optimizer improves what the data shows it is getting wrong, and by the second run there was very little left to show.

Three further constraints qualify these results, and none of them are visible in the accuracy figures alone.

These limitations fall into three groups: the data the optimizer learns from, the method itself, and the models we could afford to run. The first group concerns the input. The verdict file is the ground truth, so a systematic bias in the judge misdirects the whole search rather than merely misgrading one case. The argument in \cref{sec:optimizer-evaluation} concerns random error, which a single prompt cannot absorb, whereas a consistent bias would be learned instead of discarded. Related to this, a perfect score on a small file with most of its cases on one agent shows fit to that file rather than a prompt that generalizes, which is why per-agent accuracy is always reported next to the aggregate. Both are answered by larger and more evenly distributed verdict files rather than by changing the optimizer.

The second group is inherited from OPRO. The method needs a starting prompt, and reducing how much the result depends on that starting point is named as an open problem \autocite{yang2023llmoptimizers}. We seed each run from the live production prompt, so a weak production prompt would pull the whole search toward it. The method also gives no guarantee that each round improves on the last, because model behavior is sensitive to small changes in wording, which is why several candidates are generated per round. The drop in round 3 of \cref{fig:optimization-dashboard} is this effect rather than a fault. Finally, the paper notes that prompt optimization needs a training set of at least tens of cases for the result not to overfit badly \autocite{yang2023llmoptimizers}, so our smaller runs sit close to the lower bound of what the method supports. The third group follows from cost. We had no institutional token budget (\cref{sec:local-models}), so both the writing and the scoring model were chosen as the cheapest options that met their requirements, and neither is a strong model. This matters because OPRO depends on the writing model reasoning about why a prompt fails, so a weaker writer proposes weaker rewrites, and the improvements reported here are a lower bound on what the method can deliver rather than a measure of it. Scoring on a small model is the more serious constraint, since the prompt is tuned to the routing behaviour of that specific model. The prompt is optimal for the scorer, not for routing in general, but moving to a different model would only require rerunning the optimization.

Taken together, these constraints point the same way. The gains reported here were produced by the cheapest models that met the technical requirements, working from a starting prompt the team had already tuned by hand. A stronger writing model or a larger and more evenly distributed verdict file, with less purposefully ambiguous prompts would each be expected to improve on this, which makes the numbers in \cref{sec:empirical-label-divergence} a conservative estimate of what the loop can achieve.

\subsection{Divergence Between Judge Labels and Golden Labels}\label{sec:empirical-label-divergence}

The synthetic training queries retained their predefined golden labels. This made it possible to evaluate the same Router decisions in two ways: first, by checking whether the selected agent matched the golden label, and second, by checking whether the judge preferred the selected agent's generated answer over the alternative answer. On the complete 1,000-query training run used in this final experiment, the strongest prompt achieved 99\% accuracy against the golden labels, while the judge-derived evaluation reported 94\% for the same configuration. This experiment is separate from the 548-case optimizer comparison reported in \cref{sec:optimizer-evaluation}.

The five-percentage-point gap does not necessarily mean that either measurement is internally inconsistent. The two signals measure related but non-identical targets. The golden label grades a closed-set classification decision: it asks whether the Router selected the agent assigned to the query when the dataset was created. The judge instead performs a pairwise assessment of generated answers. Its verdict therefore depends not only on the intended agent class, but also on the particular answers generated for that run and on which alternative the Router placed next in its ranking.

Three mechanisms can consequently produce disagreement:

\begin{enumerate}
\item \textbf{Ambiguous task boundaries.} Some synthetic queries plausibly fit more than one agent. The golden dataset must nevertheless assign one label, whereas two candidate agents may both return useful answers. The judge can prefer the alternative even when the Router selected the predefined golden agent.
\item \textbf{Answer-generation variance.} The judge is intended to assess routing decisions, but it does so by comparing the answers produced by the selected agent and the strongest alternative. Variation in those answers can therefore make a correct route appear worse, or an incorrect route appear better, in a particular run.
\item \textbf{Router-dependent candidate selection.} The judge compares the selected answer with a high-ranked alternative rather than independently classifying the query across all eight agents. If the correct agent is absent from the compared candidates, the judge cannot recover it. As the Router prompt changes, the candidate pairs presented to the judge change as well.
\end{enumerate}

Further disagreement could be caused by additional LLM-judge biases. However, the experiment does not support attributing the complete five-point difference to judge error alone. The judge's agreement with ground truth was measured in a separate experiment. It therefore cannot be used to adjust the 94\% result directly.

Despite the difference in absolute values, judge-assessed accuracy moved in the same direction as golden-label accuracy across the optimization runs. Configurations with higher golden-label accuracy also received higher judge-assessed accuracy. The judge signal was therefore useful for ranking prompt candidates and steering optimization, even though it did not reach perfect agreement with the ground-truth labels. The 94\%-rated prompt was the best-performing candidate according to the signal available to the optimization pipeline and was consequently selected for deployment.

In a production environment, golden labels are unavailable for ordinary traffic, so the judge becomes the operational reference signal. If the same discrepancy occurred in production, monitoring would report 94\% even though a later human-labelled audit might estimate performance closer to 99\%. This example should not be interpreted as a stable five-point correction factor: without periodically sampled human labels, neither the direction nor the size of the gap can be assumed to remain constant. The practical implication is that judge-based monitoring can guide optimization, but it should be calibrated periodically against independently labelled production samples, as Julian Kappler and Rainer Bomblies already recommended during the Sprint 3 review (\cref{sec:sprint3-review}).

\subsection{Final Evaluation and Deployment}\label{sec:empirical-final}

The prompt selected in the first experiment was saved as a new Stage 2 prompt version and deployed in the showcase application. Re-running Stage 2 alone on the fixed 240-query evaluation set produced 100\% routing accuracy, compared with the 83\% baseline. Because the dataset and routing stage remained unchanged, this 17-percentage-point improvement can be attributed to the optimized Stage 2 prompt within the experimental setting. The final run then restored the complete two-stage pipeline: judge-confirmed examples from the separate 1,000-query training set were written to the Stage 1 example store, while Stage 2 reused the optimized prompt because it had already reached 100\% accuracy on the fixed evaluation set. This allowed the final experiment to measure how much Stage 1 could reduce LLM use while preserving the Stage 2 accuracy gain.

The resulting two-stage configuration reached 98\% accuracy while resolving 188 of the 240 queries through Stage 1. Stage 1 therefore covered 78\% of the dataset and avoided the corresponding Stage 2 LLM calls. Average latency decreased from 669 ms to 407 ms, a reduction of 262 ms or 39\%. This measured reduction is conservative relative to a production deployment because the prototype generated embeddings on the project's comparatively slow Python worker. Using a production-grade embedding provider would substantially reduce Stage 1 latency and therefore make the overall latency saving considerably larger. The two-percentage-point reduction relative to the optimized Stage 2-only configuration was the accepted trade-off for the efficiency improvement. These configurations answer different empirical questions: the Stage 2-only comparison isolates the effect of prompt optimization, whereas the two-stage result evaluates the accuracy--efficiency trade-off of the complete Router.
